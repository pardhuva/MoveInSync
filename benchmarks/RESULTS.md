# Load Test Results

Generated by `LoadSimulation` (`src/test/java/.../loadtest/LoadSimulation.java`).

Reproduce with:

```bash
mvn -Dtest=LoadSimulation -DargLine="-Xmx3g -Xms1g" test

# Scale it:
mvn -Dtest=LoadSimulation -Dload.connections=10000 -Dload.cabs=2000 -Dload.durationSeconds=20 -DargLine="-Xmx3g" test

# Diagnostics:
mvn -Dtest=LoadSimulation -DargLine="-Xmx3g -Dload.killNode=false" test
# Steady state, no node kill

mvn -Dtest=LoadSimulation -DargLine="-Xmx3g -Dharness.sharedSosPool=true" test
# A/B: no dedicated SOS pool
```

## The SOS p99 Regression, and What It Actually Was

Mid-remediation, a run reported **SOS p99 = 10,431 ms**, apparently breaking the 2-second target. It was diagnosed through controlled measurement:

| Experiment (identical settings, one variable changed) | SOS p99 | Conclusion |
|---|---:|---|
| After Steps 1–4, node kill on | 10,431 ms | Regression present |
| Express `tryLock` fix | 9,137 ms | Express write-lock blocking was not the main cause |
| Ordered dispatch fully bypassed | 10,009 ms | Ordered dispatch was not the cause |
| Node kill disabled | 7 ms (max 233 ms) | Regression was in the kill/reconnect path |
| Sample count | 7,511 vs ~5,250 expected live (1,050 × ~5 subscribers) | ~2,260 extra samples |

**Root cause: a measurement defect, not a delivery regression.**

Step 2 (critical-event history) made the system correctly replay missed historical SOS events to reconnecting clients.

The load generator matched any frame containing `"type":"SOS"` and calculated `now - originTimestamp` against the live 2-second target. Therefore, an SOS published at T+2s and recovered at T+12s was recorded as a 10-second "SOS latency".

That measurement represented the client's offline time, which the server cannot bound. It was not live-delivery latency.

The old baseline had the same defect in milder form because it replayed fewer SOS events. Therefore, even the 471–482 ms baseline was slightly inflated.

**Fix: distinguish replayed events from live deliveries.**

Resume-path frames are now marked `"replay": true` through:

- `FrameCodec.replayEvent`
- `ClientConnection.sendReplayEventNow`

A security desk must not re-sound an alarm for an SOS it is merely recovering. The benchmark now measures live delivery against the 2-second target while counting recovered SOS separately.

After the fix, the historical sample count was exactly 5,000 = 1,000 SOS × 5 subscribers, confirming the diagnosis.

Two genuine smaller defects were also found and fixed:

1. `expressDrain` blocked on `writeLock.lock()`, parking the small express pool behind 256-frame batch writes. It also re-armed itself after a failed acquisition, creating a busy-loop. It now uses `tryLock` and only re-arms when it actually did work.
2. `SnapshotStore.record` overwrote latest-state unconditionally. An out-of-order record could therefore install a stale location or status as the latest state. Writes are now sequence-monotonic.

## Dedicated SOS Express Pool: A/B Evidence

| Configuration | SOS p99 (3 historical runs) |
|---|---|
| Dedicated express pool (default) | 6 / 22 / 60 ms |
| Shared writer pool | 126 / 138 / 140 ms |

The dedicated pool performed consistently better in these measurements.

Under the case study's "frozen security desk" scenario, it is also important for preventing SOS starvation. With a shared, saturated pool, SOS is starved entirely. This is tested by:

`SosPriorityUnderPoolSaturationTest.sharedPoolStarvesSosUnderSaturation`

The dedicated-pool test delivers the same SOS in under 2 seconds.

## Interpretation

- **Latest live SOS p99 is 38 ms**, comfortably inside the 2-second requirement, during a run that kills a gateway holding half the connections.
- **2,704 SOS deliveries were recorded after the node kill**, including 1,356 recovered through resume. These figures describe this simulation run.
- **Throughput was 22,308 frames/s** on the recorded 12-core Windows 11 environment.
- The simulation demonstrates application-level recovery and delivery behavior under the tested failure scenario. It does not establish real-network latency or production-scale capacity.

## Caveat: In-Process Transport

The load generator uses **in-process transports**, not real TCP sockets.

The reported latency is **application-pipeline latency**, covering:

- Sequencing
- Ordered dispatch
- Cross-node fan-out
- Bounded outbound queues
- Location conflation
- JSON serialization

It deliberately excludes real network round-trip time and operating-system socket scheduling.

"Socket write duration" is therefore not a meaningful measurement in this harness: an in-process `send` is a list append.

This isolates the fan-out layer from the test machine's socket limits. A real-socket test against the Docker Compose topology is the natural next step. The Docker Compose topology and WebSocket demo client are available, but a real-socket load test was not run in the authoring environment because Docker was unavailable there.

## Redis Verification

Redis-backed integration tests passed against **Memurai**, a Redis-protocol-compatible Windows development server.

This verifies the Redis protocol interactions exercised by those tests. It does not establish production deployment behavior against a dedicated Redis or Redis Cluster instance.

A production Redis deployment should still be validated for its configuration, persistence, failover, resource limits, and operational behavior.
